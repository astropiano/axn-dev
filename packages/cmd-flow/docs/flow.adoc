== Flow Testing

Run XML-defined agentic flow tests against Docker Compose scenarios.

[source,bash]
----
axn-dev flow -f flows/example.xml
axn-dev flow -f flows/example.xml -m llama3.1:latest
axn-dev flow -f flows/example.xml -t "how late"
axn-dev flow -f flows/example.xml --no-stop    # keep scenario running after test
axn-dev flow -f flows/example.xml --clean-start --yes   # wipe data and run without prompting
----

The `--clean-start` flag stops the scenario(s), removes their named Docker volumes, and starts them fresh before the flow runs. It does not rebuild images. It is not compatible with `--infra`.

A flow file describes one or more `<flow>` elements with scenarios, models, a user message, and assertions. The built-in `tsAdapter` runs TypeScript/Playwright scripts; all other adapters come from plugin packages — `http` (generic, bundled with `cmd-flow`), `keycloak` (`@axn-dev/adapter-keycloak`), or any adapter an installed plugin declares — or from script files resolved per step. Assertions: `num_responses`, `contains`, `exitCode`, `duration`, `script`, `screenshot` and `llm`. Reports are written to `flows/.reports/` next to the flow file.

=== Assertion scoping

Assertions judge captured *stdout* — step output, adapter responses, `<extract>` reads — accumulating in one buffer per flow. Placement decides which slice of that buffer an assert sees:

* *Nested in a producing step* (`<step>`, `<usermessage>`, `<extract>`, custom tags) — judges *that step's own output only*; `that="duration"` measures its wall-clock ms.
* *Bare `<assert/>` or `<assertions>`* — sees *all* output accumulated since the flow started (or since the current `<repeat>` iteration started): cumulative, not just the last step.
* `fresh="true"` (on `<assert>` or the whole `<assertions>` group) — sees only output produced *since the previous assertions unit*. A `fresh` first assert behaves like a normal one.

After every assertions unit — a bare `<assert/>` counts as a one-element block — an internal cursor moves to the end of output; `fresh` asserts evaluate the slice since that cursor. All asserts inside one `<assertions>` group share the same window.

Use `<assertions>` only for two things: `desc=`/`description` (a named report group — labels its asserts in reports and the serve view) or a shared `fresh="true"` for the whole group. With neither it changes nothing — it does *not* create a sub-scope.

[source,text]
----
<step/> 1  <step/> 2  <step/> 3
<assert/>                     → sees 1,2,3
<step> 4 <assert/></step>     → sees 4 only (nested = step-scoped)
<assert/>                     → sees 1,2,3,4  (cumulative)
<step/> 5
<assert fresh="true"/>        → sees 5 only
<step/> 6  <step/> 7
<assertions>
  <assert/>                   → sees 1..7 — NOT just 6,7
</assertions>
<assertions fresh="true">
  <assert/>                   → sees 6,7
</assertions>
----

=== Screenshot assertions

`<assert that="screenshot" value="refs/button.png" .../>` captures a page — or a single HTML element — with headless Chromium and compares it pixel-by-pixel against a reference PNG stored next to the flow file (`value` is resolved relative to the flow file). Anti-aliasing noise is ignored, but structural changes (a button that moved, or went from rectangular to rounded) fail the assertion.

[source,xml]
----
<assertions>
  <!-- element: crop to #buy; also fails if the button moved position -->
  <assert that="screenshot" value="refs/buy-button.png" selector="#buy"
          url="${BASE_URL}/shop"/>
  <!-- whole viewport page -->
  <assert that="screenshot" value="refs/shop.png" url="${BASE_URL}/shop"
          viewport="1280x800" wait="500"/>
</assertions>
----

Attributes:

`value` (required):: Reference PNG path, relative to the flow file.
`url`:: Page URL; supports `${VAR}`/`${VAR:-default}` expansion against the flow env. Defaults to `BASE_URL`.
`selector`:: CSS selector — capture only this element. The image is cropped to the element's own box, so it detects content/shape changes (text, color, border-radius, …) but is blind to *position*: a moved element looks identical. To catch moves, select a container element or omit `selector` for a whole-page capture.
`fullPage`:: `true` = capture the full scrollable page (only without `selector`).
`maxDiff`:: Max allowed fraction of differing pixels, `0..1` (default `0.01` = 1%).
`threshold`:: Per-pixel color distance threshold `0..1` (default `0.1`).
`viewport`:: `"WxH"` (default `1280x800`).
`wait`:: Settle wait — milliseconds (`"500"`) or a CSS selector to wait for after page load.

On failure, the actual capture and a highlighted diff image (red = real diff, yellow = antialiasing) are written to `flows/.reports/screenshots/`. Run with `AXN_FLOW_UPDATE_SCREENSHOTS=1` to create or refresh a reference. Requires `playwright-core` and a Chromium build (`npx playwright install chromium`).

=== LLM-judged assertions

`<assert that="llm">` hands the captured output to a *judge* — an LLM or a binary judge service — and passes when the judge's verdict is positive. The rubric comes from `prompt` (or `value`, or the tag body); `judge` selects the evaluator, falling back to `$AXN_JUDGE`. No dedicated eval infrastructure is required — a local Ollama model or any OpenAI-compatible endpoint works:

`judge="ollama/<model>"`:: Local Ollama (default `http://localhost:11434`, override with `OLLAMA_BASE_URL`) — e.g. `ollama/llama3.1`. Zero setup beyond `ollama pull`.
`judge="openai/<model>"`:: OpenAI API — needs `OPENAI_API_KEY`; `OPENAI_BASE_URL` retargets to *any* OpenAI-compatible endpoint (proxies, gateways, self-hosted vLLM, …).
`judge="claude[/model]"`, `judge="gemini[/model]"`, `judge="codex[/model]"`, `judge="devin[/model]"`:: A local agent CLI in one-shot mode — spawns `claude -p`, `gemini -p`, `codex exec`, or `devin -p` with the rubric and output as the prompt and scans stdout for a PASS/FAIL verdict. The `/model` suffix adds the CLI's model flag (`--model` for claude/devin, `-m` for gemini/codex). Useful when no inference endpoint is around but an agent CLI is installed.
`judge="http(s)://…"`:: A binary judge service POSTed `{"prompt": <rubric>, "response": <output>}` that replies `{pass|passed|verdict|result|ok|success: true|false}`, a bare JSON boolean, or text containing PASS/FAIL.
`judge="<plugin-name>[/<arg>]"`:: A judge contributed by an installed plugin via `axn-dev.judges` — see `docs/plugins.adoc` ("Contributing a flow judge").

`AXN_JUDGE_TIMEOUT_MS` overrides the 60s judge timeout.

[source,xml]
----
<flow name="chat-eval">
  <scenarios>
    <scenario name="app-dev" service="app-server" adapter="http"/>
  </scenarios>
  <setup>
    <models>
      <model provider="ollama" name="llama3.1:latest"/>
    </models>
  </setup>
  <steps>
    <usermessage value="What time is it in Berlin?">
      <assert that="llm" judge="ollama/qwen2.5:14b"
              prompt="The reply states a concrete time for Berlin"/>
      <assert that="duration" max="5000"/>
    </usermessage>
  </steps>
</flow>
----

Note the two distinct models: `<model>` is the model *under test* (sent by the
`http` adapter to the chat endpoint); `judge="ollama/qwen2.5:14b"` is the
*evaluator* — ideally a different, stronger model than the one being tested.

For flaky-but-generally-good behavior — the typical LLM-evaluation case — wrap the probe in `<repeat>` and require a pass *rate*:

[source,xml]
----
<steps>
  <repeat num="10" success="0.8">
    <usermessage value="What time is it?"/>
    <assertions>
      <assert that="llm" prompt="states a concrete time" judge="ollama/llama3.1"/>
    </assertions>
  </repeat>
</steps>
----

`success` accepts a count, fraction (`"0.8"`), or percent (`"80%"`). The block reports `repeat: {runs, succeeded, needed, failures[]}` detail in the JSON report; each iteration's assertions see only that iteration's output.

In browser flows, `<extract>` pulls a DOM element into the output stream so the judge sees exactly the rendered answer rather than raw responses:

[source,xml]
----
<steps>
  <step src="steps/ask-question.ts"/>
  <extract selector=".chat-history .bubble:last-child"/>
  <assertions>
    <assert that="llm" prompt="the reply mentions Berlin" judge="ollama/qwen2.5:14b"/>
  </assertions>
</steps>
----

==== Testing the harness without an LLM

The `http(s)://` judge form makes the whole pipeline runnable offline — point `AXN_JUDGE` at a stub that returns a canned verdict:

[source,bash]
----
node -e 'require("http").createServer((q,s)=>{let b="";q.on("data",d=>b+=d);q.on("end",()=>{s.end(JSON.stringify({pass:true}))})}).listen(8788)' &
AXN_JUDGE=http://127.0.0.1:8788 axn-dev flow my-eval.xml
----

=== Flow tags

Flows can be tagged for grouping and filtering in `axn-dev serve`:

[source,xml]
----
<flow name="app-e2e">
  <tags>
    <tag>myapp</tag>
    <tag>myapp/e2e</tag>
    <tag>ux</tag>
  </tags>
  <scenarios>...
  </scenarios>
  ...
</flow>
----

Tags may be plain words (`myapp`, `ux`) or slash-separated folder paths (`myapp/e2e`). In `axn-dev serve` the tag search matches prefixes and path segments, so searching for `myapp` also shows flows tagged `myapp/e2e`.

=== Step, message, and assertion descriptions

You can also put the description inside the tag body when the real content is provided elsewhere:

[source,xml]
----
<steps>
  <usermessage value="What time is it?">Ask about the current time</usermessage>
  <step src="steps/login.ts" myArgs="xyz">Login of user</step>
  <assertions>Login should succeed
    <assert that="contains" value="welcome"/>
  </assertions>
</steps>
----

For `<step>` and `<usermessage>`, the tag body becomes the `description` when a `src` or `value` attribute provides the actual content. For `<assertions>`, the tag body (before the `<assert>` children) becomes the description.

=== Reusable step files

A step can be factored out into its own `.xml` file and bound by name. The
file must contain exactly one step element — a `<step>`/`<script>`, a
`<usermessage>`, an `<assertions>` block, or a custom adapter tag — either as
the root element or wrapped in a single-child `<steps>`.

[source,xml]
----
<!-- flows/steps/login.xml — binds the TS script next to the step file -->
<step src="ft-login.ts"/>
----

In the flow, `<step action="login"/>` binds `login.xml`. Step files are
looked up in the flow's own directory, its `steps/` subdirectory, and every
directory named in an `include` attribute (comma-separated, relative to the
flow file) on `<flows>`, `<flow>` or `<steps>`:

[source,xml]
----
<steps include="../shared/step-lib, ../shared/more-steps">
  <step action="login" user="mom"/>
  <step file="steps/logout.xml"/>
</steps>
----

Rules:

* `src`/`script` paths inside the step file resolve relative to the step
  file's directory (`script` is an alias for `src` on `<step>`).
* If the same name exists in several step dirs, the flow fails with the
  candidate list — disambiguate with `<step file="..."/>`.
* `file=` must point to an `.xml` file and cannot be combined with `src` or
  `adapter`.
* `action=` is only a step-file reference on a plain `<step>`; with
  `adapter="..."` it stays an adapter argument (e.g. `action="createUser"`).
* `file=` and `action=` cannot be combined.
* Extra attributes on the referencing step merge into the bound step's args
  (caller wins); `desc`/`description` or tag text override the description.
* Step files may reference further step files; circular references are an
  error.

=== Reserved names

The engine owns a fixed vocabulary. Self-declared names — custom step tags
inside `<steps>` and the action names bound by `<step action="name">` / step
file basenames — must not reuse it:

* *Step elements*: `usermessage`, `step`, `script`, `assert`, `assertions`,
  `picture`, `video`, `repeat`, `extract`
* *Structural elements*: `flows`, `flow`, `steps`, `scenarios`, `scenario`,
  `setup`, `models`, `model`, `env`, `var`, `readiness`, `tags`, `tag`,
  `description`, `tool-mode`, `use-docker`
* *Step-ref keywords*: `file`, `action`, `include`, `src`

A `<file .../>` element inside `<steps>` therefore fails parsing — the engine
would interpret the name before any adapter dispatch could see it. Likewise
`<step action="file">` is rejected: rename the step file. Plugin adapters may
not declare these tags in their `axn-dev.flowAdapters` manifest either —
reserved tags are dropped with a warning at registration (`usermessage` is
the exception: serving it is how message adapters work).

=== Validation

`axn-dev flow` validates a flow file at load time — including step files
bound via `action=`/`file=` — and fails with a precise error instead of
misbehaving mid-run. Beyond the reserved-name rules and the per-element
requirements documented above (`<extract> selector`, `<repeat> num`, …), the
checks are:

* a `<flow>` needs `name` and at least one step; flow names must be unique
  within a file
* `<scenario>` needs `name` and `adapter`; `<model>` needs `provider` and
  `name`; `<env><var>` needs `name`; `<readiness>` `port`/`timeout` must be
  numeric
* `<usermessage>` needs a message (`value=` or body text); a `<step>` needs
  `src=`, inline text, an `action=`/`file=` reference, or `adapter=`
* `<picture>`/`<video>` need `name`; `<video>`/`<repeat>` need child steps
* `<assert>` needs a known `that` (`contains`, `num_responses`, `exitCode`,
  `screenshot`, `llm`, `duration`, `script`), plus the attributes that type
  uses: `value` for `contains`/`num_responses`/`exitCode` (integer for the
  latter two), a reference path for `screenshot`, a rubric (`prompt`/`value`)
  for `llm`, a bound (`min`/`max`/numeric `value`) for `duration`, a script
  path for `script`

=== Evidence capture

`<picture>` and `<video>` are inline step units — like `<assertions>` they can
sit anywhere between steps and capture evidence at that point in the run.
Both require an orchestrator-driven `tsAdapter` flow (a browser must exist);
on other adapters the run fails with an error.

[source,xml]
----
<steps>
  <step src="steps/login.ts">Log in via Keycloak</step>

  <picture name="after-login" />                        <!-- viewport screenshot -->
  <picture name="grid" selector=".data-grid" /> <!-- element screenshot -->
  <picture name="full" fullPage="true" />               <!-- full scrollable page -->

  <video name="booking">                                <!-- start recording -->
    <step src="steps/open-booking.ts" />
    <step src="steps/confirm.ts" />
  </video>                                              <!-- stop + save .webm -->

  <assertions><assert that="exitCode" value="0"/></assertions>
</steps>
----

`<picture name="..."/>` captures a screenshot where it sits in the step order:
the viewport by default, a single element with `selector`, or the whole
scrollable page with `fullPage="true"`.

`<video name="...">` wraps the steps it should record. Steps inside execute
normally; the recording boundaries are driven by the orchestrator's
`videoStart(name, dir)` / `videoStop(name)` hooks (see below). If a step inside
the video fails, the recording is still finalized so the evidence is kept.

Artifacts are written to `flows/.reports/evidence/<flow>-<timestamp>/`
(alongside the JSON reports in the gitignored `.reports/` dir) and listed in
the JSON report under `flows[].evidence` (`{kind, name, path}`).
The `axn-dev serve` report view renders screenshots inline and plays videos.

==== Evidence in manual runs

In manual mode (`--manual` or the serve manual view) the human supplies the
evidence: every step card has an "Attach evidence" file input (web) or an
"Attach evidence file" prompt (CLI). This is especially useful for failed
steps — attach a screenshot of the broken state. Files land in the same
`.reports/evidence/` layout and are recorded with their `stepIndex`, so
the report shows them next to the step they belong to.

==== Orchestrator contract

An orchestrator module exports `start(baseUrl, env)`, `run(steps)` and
`stop()`. For `<video>` support it additionally implements:

* `videoStart(name: string, dir?: string)` — begin recording. Prefer recording the live page in
  place (Playwright `page.screencast.start({ path })`) over swapping in a `recordVideo` browser
  context: a swap reloads the page, so state such as an open dialog does not carry across
  `</video>` and a `<picture>` right after it captures a page still loading.
* `videoStop(name: string)` — stop recording, finalize the artifact in `dir`,
  and return its absolute path (or `void`).

The host splits each `run()` batch at video boundaries and calls the hooks
between segments, so `run()` itself never sees markers. Orchestrators without
the hooks fail with a clear error when a `<video>` step runs.

=== Plugin adapters

Flow adapters are contributed by plugin packages via the
`axn-dev.flowAdapters` manifest (see `docs/plugins.adoc` at the repo root). An adapter name on
`<step adapter="...">`, `<usermessage adapter="...">` or
`<scenario adapter="...">` resolves to a registered plugin adapter, which
runs in-process with a typed context (`env`, `baseUrl`, `scenario`, `model`,
`runScript`, ...). An adapter may also own custom step tags — a
`<keycloak .../>` step, for instance, dispatches to the adapter declaring the
`keycloak` tag in its manifest.

`axn-dev flow list-adapters` lists the registered adapters and their tags.
`http` (generic POST of the `usermessage` to a scenario base URL) is bundled
with `cmd-flow`; `keycloak` ships as `@axn-dev/adapter-keycloak`. Further
adapters — including ones that serve custom XML tags — come from installed
plugins.

=== External script adapters

Any `<step>` whose `adapter` name is *not* a registered plugin adapter falls
back to a script file. `axn-dev` resolves the name in this order:

1. `--adapter <name=path>` on the command line
2. `adapters:` in `.axn-dev/config.yaml`
3. The file pointed to by the step's `src` attribute (relative to the flow file)
4. `adapters/<adapter>.ts`
5. `adapters/<adapter>.js` next to the flow file

The adapter is executed with `tsx` (for `.ts`) and receives the whole `ParsedStep` JSON in `process.env.AXN_STEP`, plus the merged flow environment variables. Product-specific logic such as a Keycloak adapter can therefore live in the product repo instead of `axn-dev-cli`.

[source,xml]
----
<step adapter="keycloak" action="createUser"
      username="schmid_mom" email="mom@schmid.family"
      firstName="Mara" lastName="Schmid" password="schmid_mom"
      role="admin">Create a fresh parent user</step>
----

The corresponding `adapters/keycloak.ts` reads the action and attributes from `process.env.AXN_STEP` and prints the result to stdout.

=== Device targets

`axn-dev flow -i <device>` runs tsAdapter flows against a deployed device. The
device is resolved from `devices/<device>/device.yaml` under the configured
`infra:` repo (see the infra plugin docs for the repo layout). The device's
`host` becomes `BASE_URL`; `devices/<device>/.env` entries are merged into the
flow environment.

=== Deployment targets

Flows do not need a local Docker Compose scenario — any already-running
deployment (Kubernetes, a VM, a preview environment, …) can be the target.
Two ways to point a flow at one:

`--base-url <url>`:: Run-level override — applies to every scenario in the
run. Cannot be combined with `--infra`, `--clean-start`, `--port` or
`--auto-port`.
`url=` on `<scenario>`:: Pins a deployment in the flow file — useful for
fixed environments like staging, and for mixing local scenarios and
deployments in one flow. `${VAR}` references expand against process + flow
env. `--base-url` overrides it.
`base-url=` on `<flow>`:: Flow-level default deployment URL — applies to
every scenario lacking `url=`, and lets a flow omit `<scenarios>` entirely
for tsAdapter runs. Precedence: `--base-url` > `url=` > `base-url=`.

[source,xml]
----
<scenario name="staging" adapter="tsAdapter" url="https://staging.example.com"/>

<!-- scenario-less: the flow IS the deployment target -->
<flow name="smoke" base-url="https://staging.example.com" orchestrator="orchestrators/pw.ts">
  <steps><step src="steps/smoke.ts"/></steps>
</flow>
----

With a deployment target the engine performs no scenario lifecycle — nothing
is resolved, started, or stopped (the `<scenario>` `name` is a label only).
The step environment gets `BASE_URL=<url>` plus `SCENARIO_PORT` when the URL
carries an explicit port. Declared `<readiness>` probes address the base URL
directly (`service`/`port` attributes are ignored — there is no endpoint
map); a deployment with no probes runs immediately without a default probe.
Deployment targets work for both `tsAdapter` and `<usermessage>` plugin
adapters — unlike `-i`, which is tsAdapter-only.

=== CI usage

`axn-dev flow` exits non-zero when any flow fails, so pipelines can gate on
it directly. For CI logs, `--quiet` suppresses scenario lifecycle noise
(compose output, adapter resolution, repeat progress) — warnings, the
target deployment, failures and the result summary still print, and the
captured compose log is replayed to stderr if a scenario fails to start.

`--report <path>` writes an extra machine-readable report next to the
default `flows/.reports/*.json`; `--report-format junit` produces JUnit XML
(one testsuite per flow×model, one testcase per assertion) for CI test
reports:

[source,bash]
----
axn-dev flow -f flows/e2e.xml --quiet --report junit.xml --report-format junit
----

[source,yaml]
----
# .gitlab-ci.yml
test:
  script: axn-dev flow -f flows/e2e.xml --quiet --report junit.xml --report-format junit
  artifacts:
    when: always
    reports:
      junit: junit.xml
----

On GitHub, a failing flow fails the job step on its own; a JUnit reporter
action renders the results in the PR checks:

[source,yaml]
----
# .github/workflows/flows.yml
name: flows
on: [push, pull_request]
jobs:
  flow-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      # checkout the axn-dev-cli + your repos, run axn-dev setup, then:
      - run: axn-dev flow -f flows/e2e.xml --quiet --report junit.xml --report-format junit
      - uses: dorny/test-reporter@v1
        if: always()
        with:
          name: flow-tests
          path: junit.xml
          reporter: java-junit
----

=== Keycloak adapter

The `keycloak` adapter (`@axn-dev/adapter-keycloak` plugin package) creates,
deletes or resets Keycloak users through the Admin API — either via
`<step adapter="keycloak" .../>` or the `<keycloak .../>` tag it owns.

[source,xml]
----
<env>
  <var name="KEYCLOAK_ADMIN_USER" value="admin" />
  <var name="KEYCLOAK_ADMIN_PASSWORD" value="admin" />
  <var name="KEYCLOAK_REALM" value="myapp-dev" />
  <var name="KC_URL" value="http://keycloak.localhost:${SCENARIO_PORT}" />
</env>

<steps>
  <step adapter="keycloak" action="createUser"
        username="mom" email="mom@example.family"
        firstName="Mara" lastName="Schmid" password="mom" />
</steps>
----

Supported actions are `createUser`, `deleteUser` and `resetPassword`.

=== Machine-local SSH overrides

Create `devices/<device>/device.local.yaml` (gitignored) to override SSH settings
for your machine without committing them:

[source,yaml]
----
key: ~/.ssh/id_rsa          # private key path
user: deploy               # if your local username differs
port: 2222                 # if you use a non-standard port
----
